## 1. 文档结构

```markdown
# 候选人｜AI 产品经理｜学员逐字稿搭建与压力测试

> 输入材料、目标岗位、当前日期、事实边界说明。

## 0. 如何使用这份逐字稿
## 1. 事实与证据台账
## 2. 冲突与不能说过头
## 3. 候选人定位与能力差距
## 4. 逐字稿准备清单与缺口诊断
## 5. 能力覆盖检查
## 6. 面试问题地图
## 7. 30 秒与 90 秒自我介绍
## 8. 转行动机与岗位匹配
## 9. 项目一主线与问题族逐字稿
## 10. 项目二主线与问题族逐字稿
## 11. 技术专项压力测试
## 12. M15 数据指标审计
## 13. Web/Vibe/AI Coding 产物走查
## 14. Bad Case、Eval 与项目产物走查
## 15. AI 行业判断与目标公司含义
## 16. 自我学习、自驱与行为面故事
## 17. 失败、冲突、商业化与组织落地
## 18. 陌生场景迁移与 30/60/90
## 19. 反问面试官
## 20. 面试前待补证据
```

没有第二个项目时删除项目二；不得保留空壳章节。

“如何使用这份逐字稿”必须使用学员能直接理解的语言，不要先讲方法论术语。默认写成四步：

1. 先核实事实和证据；
2. 再准备最高概率问题；
3. 然后用问题族练习追问；
4. 最后补证据、删除夸大表述。

对“事实与证据台账”的通俗解释：

> 它就是一张简历对账表，用来确认每个重要说法是否真实、做到哪一步、有什么证据，以及面试时最多可以说到什么程度。

状态只能使用：已验证事实、候选人主张、设计目标、方案假设、外部基准、推断结果。

## 3. 逐字稿准备清单与缺口诊断模板

创建完整逐字稿前，必须读取 `script-preparation-inventory.md` 并先输出：

```markdown
| 层级 | 准备维度 | 优先级 | 当前状态 | 已有回答/证据 | 具体缺少什么 | 学员下一步动作 |
| --- | --- | --- | --- | --- | --- | --- |
```

其中：

- 当前状态只能写：已准备、部分准备、未准备、N/A；
- “部分准备”必须说明是缺案例、缺数据、缺产物还是缺追问；
- 所有 P0 未准备项都要给出具体动作，不能只写“继续完善”；
- P0 基本补齐后，再继续扩展大量面试问题。

## 5. 逐字稿模块

### 面试回答素材卡怎么解释

不要只写“建议搭建回答资产”。必须告诉学员：

> 回答素材卡是你自己面试前使用的素材库，不需要交给面试官，也不是另一套要背的长篇逐字稿。一张卡整理一个事实、决策、技术证据或真实故事，可以重复回答多种问法。

同时给出明确任务：

1. 先做 6–10 张事实卡，并为每个关键数字单独做 M15 数据卡；
2. 再做 4–6 张决策卡和 4–8 张技术证据卡，其中至少一张 AI Coding 产物卡或缺口计划；
3. 补 4–5 张真实故事卡、3 张行业判断卡和 2 张学习/自驱卡；
4. 最后补商业/采纳和岗位迁移卡；
5. 每张卡写清支持哪些问题、不能说什么、还缺什么证据；
6. 用同一张卡分别练习 15 秒结论、60 秒回答和追问展开。

不得只列卡片名称。至少提供一份卡片模板和一个基于候选人材料、不虚构事实的示例。

### 自我介绍

- 30 秒：定位、年限/背景、一个最强证据、目标岗位。
- 90 秒：背景连续性、核心项目、个人贡献、结果口径、诚实边界。
- 不堆技术词；最多留 1-2 个可深挖钩子。

### 项目主线

建议控制在 3-5 分钟：

1. 用户和原工作流；
2. 为什么值得解决、为什么需要 AI；
3. MVP 与不做什么；
4. 关键系统链路；
5. 本人三项关键决策；
6. 产物、指标和成熟度；
7. 一个失败/限制；
8. 复盘与迁移。

### 技术专项

每个技术主张至少准备：

`系统链路 -> 选择理由 -> 实际产物/Trace -> Bad Case -> 评测 -> 成本/风险取舍 -> 本人边界`。

### M15 数据指标卡

每个关键数字单独填写；不知道就写 `[待补证据]`，不能由模型补算：

```markdown

- 决策目的、定义和统计单位：
- 分子：
- 分母与排除项：
- 来源、样本量、抽样和关键切片：
- 统计周期、轮次和 Ground Truth：
- 优化前基线：
- 优化后/对照方式：
- 计算阈值、波动/稳定性：
- 同期变化、归因和反面证据：
- 质量/风险/延迟/成本/覆盖率护栏：
- 用户/业务结果：
- 实测/目标/基准/推断状态与可复核证据：
- 面试时最多可以说到：
```

### AI Coding 产物卡

```markdown
#### AI Coding 产物卡：
- 用户问题、为什么需要 Coding：
- 可运行产物与输入→数据/接口/AI→输出链路：
- AI 生成什么，我定义/修改/决策什么：
- 测试清单和一个 Debug 案例：
- 密钥、隐私、鉴权、依赖和注入/XSS 检查：
- 部署、监控、回滚、维护和工程边界：
- 缩短的验证周期、用户反馈和改变的产品决策：
```

### AI 行业判断卡

准备 `共识趋势 / 非共识判断 / 目标公司影响` 三张：

```markdown
#### 行业判断卡：
- 具体变化、来源和日期：
- 事实 / 推断 / 个人判断：
- 变化机制和用户工作流影响：
- 产品机会、商业/组织/安全约束：
- 目标公司的 Build/Buy/Partner、优先级和验证动作：
- 什么证据会推翻或修正观点：
```

### 学习与自驱卡

```markdown
#### 学习/自驱卡：
- 主动发现的真实缺口或无人布置的问题：
- 目标、资源选择和刻意实践：
- 可展示产物：
- 反馈来源；AI 辅助内容如何交叉验证：
- 失败、放弃或方向调整：
- 后续行为/决策变化、持续节奏和下一缺口：
```

## 7. 完成检查

```markdown
- [ ] 项目性质、客户、时间、团队、成熟度已经统一
- [ ] 已完成逐字稿准备清单与缺口诊断，P0 均已准备或有具体补齐动作
- [ ] 实测、目标、假设和外部基准没有混用
- [ ] 每个关键数字都有 M15 数据卡，分子、分母/排除、样本、周期、GT、基线、对照、归因、护栏和业务结果已核实或标待补
- [ ] Core 问题控制在 10-12 个
- [ ] 至少一半 Core 回答来自真实过去事件
- [ ] 每个重要主张都有产物或待补证据
- [ ] 四组技术专项已覆盖或标记 N/A
- [ ] 有真实 AI Coding 产物、测试、Debug、安全与产品影响；没有时有诚实缺口计划
- [ ] 有一个完整 Bad Case Trace
- [ ] 有失败、冲突、改判和用户发现故事
- [ ] 有三张带日期的行业判断卡，其中一张落到目标公司并包含反证条件
- [ ] 有学习闭环和主动自驱两张卡，包含产物、反馈、验证与行为改变
- [ ] 有买方、预算、验收、采纳与定价准备
- [ ] 有岗位差距、目标级别和迁移回答
- [ ] 没有连续多段相同的“三点式”AI 语言
- [ ] 能在不看全文时使用事实卡和决策卡作答
```
