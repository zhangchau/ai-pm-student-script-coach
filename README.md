# AI PM Student Interview Script Coach

面向 AI 产品经理学员的、以证据为先的面试逐字稿教练 skill。它不帮你把经历“写得更像做过”，而是把真实材料整理成可复用、可追问、经得起核验的回答系统。

适用于转行、校招、初中级 AI 产品经理，以及有 RAG、Agent、Workflow、AIGC、ChatBI、Eval、私有化部署等项目经历的候选人。

## 它能帮你做什么

- 根据简历、PRD、作品集、项目材料和目标 JD，预测高概率面试问题。
- 生成 30 秒、60 秒、3 分钟与压力追问四层回答，而不是堆砌一百篇孤立的“标准答案”。
- 建立简历对账表，区分已验证事实、个人主张、设计目标、方案假设、外部 benchmark 与推断。
- 审核每一个关键数据：指标定义、分子分母、样本、周期、基线、归因、护栏指标和业务含义。
- 针对 AI 项目补齐技术追问：检索与文档结构、Prompt/模型/编排、Eval/Trace/治理、安全与数据权限。
- 准备 AI Coding 作品、行业判断、学习闭环、自驱项目、失败复盘、买方/ROI/落地采用和岗位迁移问题。

## 适用场景

| 你现在的需求 | 这个 skill 会产出什么 |
| --- | --- |
| 还没有逐字稿 | 全套面试回答素材卡、问题地图和首版逐字稿 |
| 已有逐字稿但很空泛 | 事实冲突、证据缺口、夸大表述和需重写的段落 |
| 不知道面试官会怎么追问 | 按简历主张生成真实性、技术、指标、失败、商业和迁移追问链 |
| 正在投某个职位 | 用 JD 对齐证据优势、风险缺口和正确的目标层级 |
| 想模拟面试 | 一次只走一条关联追问链，并给出评分和下一步补证据建议 |

## 安装

### 方式一：下载 ZIP

1. 在本仓库页面点击 **Code → Download ZIP**。
2. 解压下载的文件。
3. 将整个 `ai-pm-student-script-coach` 文件夹复制到：

   `~/.codex/skills/ai-pm-student-script-coach/`

4. 重新打开 Codex，开始新对话后即可调用。

```bash
git clone https://github.com/zhangchau/ai-pm-student-script-coach.git ~/.codex/skills/ai-pm-student-script-coach
```


## 快速开始

将材料上传到 Codex，或在同一对话中说明文件位置，然后用下面的任一提示词开始。

### 从零搭建

```text
$ai-pm-student-script-coach
请根据我的简历、PRD 和目标 JD，搭建真实可信的 AI 产品经理面试逐字稿。
先做简历对账和缺口诊断，再输出最高优先级的问题族。
```

### 审核已有逐字稿

```text
$ai-pm-student-script-coach
请诊断这份逐字稿：找出事实冲突、没有证据的结果、泛泛的 AI 术语和最可能被追问的问题。
不能确认的内容请标记为 [待补证据]。
```

### 面向 JD 定制

```text
$ai-pm-student-script-coach
这是我的简历、项目材料和目标 JD。请评估我的证据与 JD 的匹配度，
给出正确的候选人定位，并重写自我介绍、项目主叙事和岗位匹配回答。
```

### 压力测试

```text
$ai-pm-student-script-coach
请作为 AI 产品经理面试官，围绕我的 RAG 项目进行压力测试。
一次只问一个与上一题相关的问题；我回答后，请按真实性、所有权、证据、技术、指标和迁移能力评分。
```

## 建议提供的材料

材料越完整，回答越具体；缺少材料并不会阻止使用，skill 会明确标注需要补充的证据。

| 优先级 | 材料 | 用途 |
| --- | --- | --- |
| P0 | 简历或简历草稿 | 提取所有主张、识别最可能被核验的内容 |
| P0 | 主要项目的 PRD、作品集或项目总结 | 还原用户、问题、决策、产物和项目阶段 |
| P1 | 目标 JD、公司与职级 | 校准岗位匹配、侧重点与目标层级 |
| P1 | 现有逐字稿或模拟面试记录 | 诊断口头表达、逻辑断点和高频追问 |
| P2 | 原型、Demo、代码仓库、截图、Trace、评测表 | 把“我做过”变成可展示的证据 |
| P2 | 数据看板、埋点口径、用户反馈、复盘文档 | 核验数字、效果和归因边界 |

请勿为了“显得完整”补造客户、用户、数据、上线阶段、代码贡献或业务结果。证据不足时，直接说明项目阶段和下一步验证计划，通常比被追问后露出矛盾更有说服力。

## 工作方式

1. **简历对账**：把每一项重要主张列为“主张 → 来源 → 状态 → 冲突 → 证据 → 安全表述”。
2. **定位与缺口**：明确你的真实优势、仅停留在设计/Demo 的能力、最大风险和合适的目标层级。
3. **问题地图**：从你的真实主张推导问题，而不是套用泛泛题库。
4. **回答素材卡**：先整理事实、数据、决策、故事、技术、商业、行业判断、学习和迁移素材，再组合成不同回答。
5. **压力测试**：按事实、个人所有权、证据、失败、取舍和迁移的顺序检验核心项目。

## 你会得到的交付物

完整模式默认围绕 60 分钟面试准备 10–12 个核心问题族，以及按问题族归类的 20–40 个追问分支。通常包括：

- 简历对账表、冲突清单与 `不能说过头` 清单。
- 候选人一句话定位、证据型能力优势、设计/Demo 边界和关键缺口。
- `逐字稿准备清单与缺口诊断`：每个维度的 P0/P1/P2 优先级、完成度、缺失材料和下一步动作。
- 面试问题族地图与能力覆盖检查。
- 30 秒、90 秒自我介绍；转行动机、why now、岗位匹配、优势/短板与目标层级回答。
- 每个核心项目的 3–5 分钟主叙事，以及用户流程、AI 必要性、MVP、非目标和路线图准备。
- 可复用的事实卡、数据卡、决策卡、故事卡、技术卡、AI Coding 卡、商业卡、行业判断卡、学习/自驱卡与迁移卡。
- 失败、冲突、被否决方案、反转判断、用户发现、买方/ROI、组织落地和 30/60/90 天计划。

## 回答的四层结构

核心问题不会只给一段长文，而会按下面四层准备。建议记住逻辑和证据锚点，不要逐字背诵。

| 层级 | 时长 | 目标 |
| --- | --- | --- |
| L0 一句话结论 | 10–15 秒 | 先给结论，让面试官知道你要证明什么 |
| L1 主回答 | 30–60 秒 | 结论、关键证据与诚实边界 |
| L2 项目展开 | 90 秒–3 分钟 | 背景、选择、行动、结果、反思与取舍 |
| L3 压力追问 | 按需 | 指标、技术、失败、反事实、商业、迁移等分支 |

## 如何理解“证据优先”

### 项目成熟度

项目会按成熟度表述，避免把概念或 Demo 写成“已上线产品”。

| 等级 | 含义 |
| --- | --- |
| M0–M1 | 想法、研究、PRD 或原型 |
| M2–M3 | 可运行 Demo 或内部测试 |
| M4–M5 | 客户 POC 或客户环境真实用户试用 |
| M6–M7 | 已验收/付费生产，或形成规模化复制 |

### 证据等级

| 等级 | 含义 |
| --- | --- |
| E0–E1 | 观点或方法框架 |
| E2 | 具体做过的行动与决策 |
| E3 | 可核验的产物、数据、版本或 Trace |
| E4 | 客户使用、独立验收或业务结果 |

如果项目只有 M0–M3，也可以回答得有竞争力：讲清楚你识别的问题、做过的验证、取舍、风险和下一步实验；不要把设计目标改写为结果。

## 数据与 AI 项目的特别检查

### M15 数据指标卡

每一个关键数字都要能回答：它衡量什么、分子和分母是什么、排除了什么、样本和切片是什么、统计周期多长、Ground Truth 如何得到、与什么基线比较、为什么能归因、护栏指标是什么，以及它如何影响业务。

例如，“准确率 98%”在没有口径、样本、周期和对照组时，不是可辩护的成果，只能算一条待补证据的主张。

### AI Coding 与 AI 技术追问

如果你声称做过 Web/Vibe/AI Coding 产物，需准备实际可运行的输出、你与 AI 分别完成的部分、测试、Debug、安全/部署边界，以及这个产物改变了哪项产品决策。

对于 RAG、Agent 或企业 AI 项目，重点准备：

- 文档结构、切分、召回、重排与权限边界。
- Prompt、模型选择、模型路由、工具调用和编排。
- Eval、Judge、Trace、Bad Case、灰度与发布治理。
- 隐私、数据治理、成本、延迟、可靠性与责任使用。

## 本地校验

生成完整 Markdown 逐字稿后，可使用内置校验器检查关键章节、事实边界、覆盖审计和 Core/Branch 划分：

```bash
python3 scripts/validate_student_script.py <你的逐字稿.md>
```

校验器会提示缺失项；它不会替你补造任何事实。请先补充原始证据或降低表述强度，再修改逐字稿。

## 常见问题

### 没有真实线上数据，还能用吗？

可以。请如实说明项目成熟度，并用用户访谈、Demo 测试、评测集、方案取舍、风险识别和下一步验证替代不存在的业务结果。skill 会把“已发生的事”和“待验证的设计目标”分开写。

### 我不是算法工程师，需要准备到什么程度？

重点是产品判断：用户任务为什么需要 AI、方案如何落地、模型和流程的取舍、如何评测、失败时如何降级，以及成本/时延/安全如何影响产品。只有你声称亲自实现的部分，才需要深入解释实现细节。

### 要把全部回答背下来吗？

不需要。更有效的方式是先填好回答素材卡，再练 L0、L1、L2 三层表达与常见追问分支。这样同一组真实证据可以稳定回答不同问法。

### 为什么没有自动生成“漂亮的数字”？

因为面试里最容易被击穿的往往正是没有口径的数字。这个 skill 的原则是：宁可明确标注 `[待补证据]`，也不把目标、benchmark 或推断包装成已验证结果。
